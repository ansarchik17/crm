## Цель и границы первой версии

Одна компания, один городской номер, SIP, до 30 сотрудников. Робот отвечает,
выясняет потребность, консультирует по подтверждённым материалам и передаёт
разговор сотруднику. После звонка сохраняются запись, расшифровка, результат
и договорённости в выбранной CRM.

30 внутренних номеров — справочник сотрудников, а не требование 30 одновременных
разговоров. Число SIP-каналов, параллельных AI-сессий и минут нужно согласовать
отдельно. Первая версия — для одного бизнеса. Полноценный сервис для нескольких
компаний потребует авторизации, изоляции данных, конфигураций и учёта расходов.

Не входит в первый пилот: собственная универсальная CRM, биллинг, массовые
исходящие обзвоны, мобильное приложение, обещание заменить всех администраторов.

## Целевая архитектура

```text
Клиент → городской номер / SIP-оператор → Asterisk
                                         ├─ очереди → сотрудники 101–130
                                         └─ ARI + двустороннее аудио
                                              ↕
                                      сервис голосового диалога
                                      STT → Qwen + знания → TTS
                                              ↓
                                   проверяемые действия → CRM

Завершённые записи → фоновая очередь → STT → Qwen-анализ → CRM
Данные звонков / события → PostgreSQL; аудио → закрытое файловое хранилище
```

Asterisk отвечает за соединения; приложение — за контекст и AI. Медиаобработка
не должна блокировать API или фоновую аналитику. Для начала — один проект
с разделением модулей, затем отдельные процессы API, аудио и worker.
Redis или другая очередь выбирается на этапе фоновых задач; сейчас не требуется.

ARI External Media позволяет подключать внешний обработчик аудио. В новых
версиях Asterisk есть `chan_websocket`, упрощающий отправку аудио по сравнению
с самостоятельным RTP. Конкретную версию АТС, транспорт и кодеки закрепим
в проверенном стенде; произвольная установленная версия может не поддерживать
нужный режим. macOS используем для разработки, Linux — для проверки АТС и SIP.

## Поведение во время звонка

Состояния: входящий → приветствие → слушание → распознавание → ответ →
озвучивание → слушание; отдельно перевод, завершение и отказ.
У каждого звонка — внутренний `call_id`; идентификаторы каналов и участков
перевода хранятся отдельно. Текстовые `session_id` текущего прототипа ещё не
являются идентификаторами телефонных вызовов.

При перебивании отменяем генерацию и очищаем очередь звука; запоздалые результаты
предыдущей реплики отбрасываем по номеру поколения. При запросе человека выбираем
разрешённую очередь или сотрудника. Модель предлагает действие, сервер проверяет
его аргументы, рабочие часы и доступность. Произвольный SIP-адрес модель не задаёт.

Подтверждать запись, заказ или изменение CRM можно только после успешного ответа
системы. Повтор действия после сетевого сбоя требует идемпотентного ключа.
Номер звонящего используется для поиска, но не подтверждает личность.
При незнакомом вопросе — уточнение или человек, при отсутствии ответа сотрудника —
согласованный сценарий обратного звонка. При отказе AI АТС сохраняет обычную
маршрутизацию. Отказ самой АТС покрывается отдельным резервным маршрутом оператора.

## Данные и интеграция

План сущностей: компании, сотрудники, очереди, звонки, участники/участки,
реплики, записи, обращения, результаты анализа и очередь событий CRM.
CRM получает минимальный набор: call_id, контакт, тема, ответственный, итог,
ссылка на запись и следующие действия. Уникальность по компании + событию
предотвращает дубли. Недоставленные события остаются в outbox с повторными
попытками и видимым статусом ошибки.

Запись должна покрывать и робота, и сотрудника после перевода. По возможности
направления пишутся раздельно; личность сотрудника привязывается к участку звонка.
Записи закрыты от публичного доступа, ссылки имеют срок действия. Правила записи,
размещения и хранения данных уточняются после выбора страны и провайдеров.

Анализ: причина, резюме, итог, договорённости, следующее действие и цитата с
временной отметкой. Если доказательства нет — поле пустое. Оценка настроения
показывается как предположение. Результат валидируется по схеме и сравнивается
с ручной разметкой, а не принимается автоматически как факт.

## Этапы с критериями готовности

| Этап | Работа | Проверяемый результат |
|---|---|---|
| 0 — начат | Анализ, структура, текстовый API | Локальный запуск и тесты; реальные API ещё не проверены |
| 1 | Документация API, тестовые аудиофайлы, выбор TTS | Реальный STT → Qwen → TTS, замеры и расчёт расходов |
| 2 | Микрофон, потоковый звук, VAD, перебивания | Несколько минут диалога без смешения реплик |
| 3 | Linux/Asterisk, два SIP-клиента | Обычный звонок и двусторонний звук робота |
| 4 | SIP-оператор и городской номер | Входящий с мобильного, корректное завершение |
| 5 | Очереди и перевод | Ответ, занятость, неответ, нерабочее время, отказ AI |
| 6 | Знания и CRM | Подтверждённая консультация, одна заявка при повторе события |
| 7 | Записи и аналитика | Весь разговор после перевода, анализ с доказательствами |
| 8 | Пилот и эксплуатация | Нагрузка, сбои, восстановление, согласованные показатели |

Этапы 1–2 решают главный технический риск: подходят ли ваши API для живой речи.
Файловый STT может быть полезен для аналитики, даже если не подходит для диалога.
Не покупать инфраструктуру на 30 параллельных AI-разговоров до измерений.

## Проверки перед реальными клиентами

- Задержки: конец речи → текст STT → первый токен → первый звук; p50 и p95.
  Ориентир 1–2 секунды до начала ответа требует проверки, сейчас не гарантируется.
- Русский и другие выбранные языки: шум, акценты, имена, услуги, телефонные цифры.
- Перебивания, тишина, обрыв, две одновременные реплики и завершение во время API.
- Неверные/долгие ответы STT, Qwen, TTS; лимиты API и недоступная CRM.
- Перевод не теряет клиента; запись продолжается, контекст доступен сотруднику.
- Повторная доставка событий не дублирует заявки и задачи.
- Согласованная одновременная нагрузка; лимиты затрат и доступность SIP-каналов.
- Неверные сведения и просьбы обойти правила не вызывают действий вне разрешений.
- Проверка доступа к записям, удаления и восстановления резервной копии.

## Экономика и открытые решения

Месячная себестоимость = номер + SIP-каналы + телефонные минуты + STT (робот
и записи сотрудников) + токены Qwen (диалог и анализ) + TTS + серверы + хранение.
Для расчёта нужны тарифы, минуты, средняя длительность, часы работы и пики.
STT одного и того же участка во время звонка и после него может оплачиться дважды:
нужно решить, когда повторное распознавание улучшает результат достаточно.

До следующего интеграционного этапа нужны:

1. STT: провайдер, документация, streaming или файлы, языки, кодеки, лимиты.
2. Qwen: провайдер, base URL, model ID, доступные режимы и квоты.
3. TTS: имеющийся сервис или разрешение выбрать по языкам и бюджету.
4. Первая отрасль, услуги и 10–20 реальных типовых вопросов без персональных данных.
5. Страна/город, текущий номер и SIP, планируемые пики вызовов.
6. CRM и API-доступ, сценарий создания обращения, расписание сотрудников.

Ключи не нужны в переписке. Срок внедрения и стоимость пока не фиксируются:
оценка зависит от проверки API, CRM, телефонии и требований эксплуатации.
