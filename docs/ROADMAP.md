# План работ: голосовой робот с телефонией, CRM и аналитикой

Обновлено: 3 октября 2026. Это действующий план реализации заказа.
Исходный аудит и обоснование архитектуры: [PROJECT.md](PROJECT.md).

## Заказ

- Один городской номер, SIP/IP-телефония.
- До 30 внутренних номеров сотрудников.
- AI-робот: понимает речь, консультирует, переводит звонок на нужного сотрудника.
- Интеграция с CRM заказчика.
- Запись разговоров и их AI-анализ.

Первая версия — для одной компании. Число одновременных разговоров с роботом
согласовывается отдельно: 30 внутренних номеров не означает 30 параллельных
AI-сессий. Не входит в заказ: собственная CRM, биллинг, массовые обзвоны,
мобильное приложение.

## Архитектура и модули

```text
Клиент → городской номер → SIP-оператор → Asterisk (Linux)
                                            ├─ очереди → сотрудники 101–130
                                            └─ ARI / media WebSocket ↔ voicecrm.telephony
                                                                           ↕
                                                     voicecrm.dialogue: STT → LLM → TTS
                                                                           ↓
                                                     voicecrm.crm: проверяемые действия → CRM
Записи звонков → voicecrm.analytics: файловый STT → LLM-анализ → CRM
PostgreSQL: звонки, сотрудники, события; закрытое хранилище аудио
```

| Модуль | Пакет | Состояние на 3 октября 2026 |
|---|---|---|
| Диалог | `src/voicecrm/dialogue` | Прототип работает: файловый STT Alem, Qwen, сессии, OpenAI Realtime без живой проверки |
| Телефония | `src/voicecrm/telephony` | Не начата, только описание ответственности |
| CRM | `src/voicecrm/crm` | Не начата, CRM заказчика не выбрана |
| Аналитика | `src/voicecrm/analytics` | Не начата |
| Хранилище | — | Нет базы данных, сессии в памяти |
| Веб-страницы | `src/voicecrm/static` | Локальные тестовые страницы `/` и `/realtime` |

Главный технический риск: текущий диалог работает по файлам и по очереди,
а телефонный разговор требует потокового звука, определения конца речи
и перебиваний. Этот риск снимается на этапах 1–2 до покупки телефонии.

## Этапы и проверяемые результаты

| # | Этап | Что делаем | Результат, который можно проверить |
|---|---|---|---|
| 0 | Прототип | Сделано: текстовый API, Alem STT и Qwen, веб-тест, Git, модульная структура | Тесты проходят, `/health` отвечает, живые запросы к Alem выполнены |
| 1 | Выбор голосового ядра | Живой тест OpenAI Realtime, сравнение с цепочкой Alem, выбор серверного TTS, расчёт стоимости минуты | Таблица задержек p50/p95 на одинаковых репликах, решение по STT/LLM/TTS с ценами |
| 2 | Потоковый диалог | Потоковый звук, VAD, перебивание, отмена генерации, отбрасывание запоздалых ответов | Несколько минут диалога в браузере без смешения реплик, задержка ответа измерена |
| 3 | Стенд телефонии | Linux-сервер, Asterisk, два SIP-клиента, справочник 30 внутренних номеров, ARI | Звонок между SIP-клиентами; робот слышит и отвечает внутри звонка |
| 4 | Городской номер | Договор с SIP-оператором, транк, входящие и исходящие | Входящий звонок с мобильного на робота, корректное завершение, обычная маршрутизация при отказе робота |
| 5 | Очереди и перевод | Очереди, рабочие часы, перевод только на номер из справочника, сценарии занятости и неответа | Робот переводит на сотрудника; занят, не отвечает, нерабочее время, отказ AI отработаны |
| 6 | Знания и CRM | Утверждённые материалы заказчика, адаптер CRM, outbox с идемпотентностью | Консультация по подтверждённым данным; одна заявка в CRM при повторной доставке события |
| 7 | Записи и аналитика | Запись обоих участков, фоновая расшифровка, анализ по схеме | Запись покрывает разговор после перевода; анализ с цитатами и временными отметками |
| 8 | Пилот | Нагрузка, сбои, восстановление, доступы, метрики | Согласованные показатели пилота выполняются на реальных звонках |

Этапы идут последовательно; этапы 3–4 можно начинать параллельно с этапом 2,
если сервер и SIP-оператор уже выбраны.

## Решения, которые нужны от заказчика

1. Страна, город, действующий SIP-оператор или право выбрать его.
2. Какая CRM используется, есть ли API и тестовый аккаунт.
3. Допустимые провайдеры речи и языковой модели: OpenAI, Alem или только локальные.
4. Языки обслуживания: русский, казахский, другие.
5. Ожидаемое число звонков в день и в пике, средняя длительность, часы работы.
6. Список сотрудников, отделов и правила перевода.
7. Утверждённые материалы для консультаций: услуги, цены, адрес, часы.
8. Правила хранения записей и персональных данных, срок хранения.

Без пунктов 1–3 этапы 3, 4 и 6 начать нельзя.

## Инфраструктура

- Разработка на macOS, стенд и прод на Linux: Asterisk не ставим на macOS.
- Один сервер для стенда: Asterisk, приложение, PostgreSQL. Разделение на процессы API,
  аудио и фоновые задачи — после этапа 5.
- Версия Asterisk, транспорт аудио (External Media или media WebSocket) и кодеки
  фиксируются на этапе 3 по результатам стенда.
- Очередь задач (Redis или другая) выбирается на этапе 7.

## Правила, которые сохраняются на всех этапах

- Ключи только в локальном `.env` и в секретах сервера; в Git и документацию не попадают.
- Модель предлагает действие, сервер проверяет аргументы и права; перевод только
  по справочнику; запись в CRM только после подтверждения системой.
- Ответы провайдеров не выводятся клиенту при ошибке.
- `/health` отражает конфигурацию процесса, а не доступность внешних сервисов.
- Каждый этап закрывается тестами и живой проверкой, результат фиксируется в `docs/`.

## Как продолжать

```sh
uv sync --locked
.venv/bin/python -m pytest -q
node --test tests/test_audio.mjs tests/test_realtime_events.mjs
.venv/bin/python -m uvicorn voicecrm.main:app --host 127.0.0.1 --port 8000
```

Ближайший шаг: этап 1. Добавить `OPENAI_API_KEY` в `.env`, перезапустить сервер,
выполнить живой тест `/realtime` и сравнить его с цепочкой Alem по одинаковым репликам.
