# EspoCRM: запуск и работа с голосовым сервисом

Обновлено: 15 октября 2026. Рабочая папка — `/Users/ansar.keles/CRM`.
EspoCRM 10.0.9 установлена как основная CRM проекта. Голосовой прототип
продолжает работать отдельным Python-сервисом. Подробный разбор основы —
[ESPOCRM_ANALYSIS.md](ESPOCRM_ANALYSIS.md); результаты последних проверок и
точка продолжения — [HANDOFF.md](HANDOFF.md).

## Что теперь открывать

| Адрес | Назначение |
|---|---|
| `http://localhost:8080` | Основной интерфейс EspoCRM: контакты, звонки, задачи, календарь и администрирование |
| `http://127.0.0.1:8001/` | Перенаправление HTTP 307 в основную CRM; адрес берётся из `ESPOCRM_URL` |
| `http://127.0.0.1:8001/voice` | Прежний голосовой тест: Alem STT → текстовый OpenAI → озвучивание браузера |
| `http://127.0.0.1:8001/realtime` | Отдельный голосовой тест OpenAI Realtime через WebRTC |
| `http://127.0.0.1:8001/docs` | Документация HTTP API Python-сервиса |
| `http://127.0.0.1:8001/health` | Настройки и состояние процесса голосового сервиса |
| `http://127.0.0.1:8001/crm/status` | Живая проверка доступа к EspoCRM через ограниченный API-ключ |
| `ws://localhost:8083` | Служебный WebSocket EspoCRM для уведомлений и обновления карточек |

WebSocket перенесён на порт **8083**, поскольку 8081 был занят. Его открывает
сам интерфейс CRM; в адресную строку браузера этот URL вводить не требуется.
Порт 8000 занят другим проектом. Не останавливайте его процессы.

Основная страница CRM и голосовые тесты имеют разные адреса. Вход в EspoCRM
не запускает разговор с OpenAI. Во время перехода на новую CRM платных вызовов
OpenAI не выполняли. Дальнейшие голосовые проверки используют настроенные
внешние API и могут тарифицироваться.

## Из чего состоит установка

[compose.yaml](../compose.yaml) запускает четыре сервиса:

| Сервис | Образ / запуск | Назначение |
|---|---|---|
| `espocrm-db` | `mariadb:11.4` | Постоянная база CRM; порт БД на хост не опубликован |
| `espocrm` | `espocrm/espocrm:10.0.9` | PHP/Apache, интерфейс и REST API CRM; порт хоста 8080 |
| `espocrm-daemon` | Тот же EspoCRM image, `docker-daemon.sh` | Запланированные и фоновые задачи CRM |
| `espocrm-websocket` | Тот же EspoCRM image, `docker-websocket.sh` | Обновления интерфейса; порт хоста 8083 |

HTTP и WebSocket публикуются только на `127.0.0.1`. Это локальный стенд.
Для доступа с других устройств нужна отдельная настройка HTTPS, домена,
доступов и правил сети.

Daemon уже отвечает за фоновые задания. Дополнительный cron для того же
экземпляра сейчас не настраивается. WebSocket CRM передаёт уведомления и
изменения записей; голосовой звук идёт через отдельный WebRTC/OpenAI-контур.

Данные сохраняются в именованных Docker-томах проекта `voicecrm-espo`:

| Том в Compose | Путь внутри EspoCRM | Содержимое |
|---|---|---|
| `espo-db` | `/var/lib/mysql` в контейнере БД | Таблицы и записи CRM |
| `espo-data` | `/var/www/html/data` | Конфигурация, внутренние данные, вложения и логи приложения |
| `espo-custom` | `/var/www/html/custom` | Пользовательские backend-настройки и расширения |
| `espo-custom-client` | `/var/www/html/client/custom` | Пользовательские настройки и расширения интерфейса |

Весь `/var/www/html` не монтируется: эта старая схема мешает обновлениям EspoCRM
10. Core находится в закреплённом image, изменяемые данные — в отдельных томах.
[Официальная схема Docker](https://docs.espocrm.com/administration/docker/installation/).

## Файлы настроек и доступов

| Файл | Назначение |
|---|---|
| `.env` | Существующие настройки OpenAI, Alem и голосового диалога |
| `.env.espocrm` | Локальные `ESPOCRM_URL`, `ESPOCRM_API_KEY`, `ESPOCRM_TIMEOUT_SECONDS`; создаётся bootstrap-скриптом |
| `runtime/secrets/espo_admin_password` | Пароль первоначального администратора `admin` |
| `runtime/secrets/espo_db_password` | Пароль пользователя БД `espocrm` |
| `runtime/secrets/espo_db_root_password` | Отдельный административный пароль БД |
| `runtime/bootstrap.json` | Идентификаторы роли, API-пользователя и ответственного для локальных проверок |
| `runtime/verification.json` | Состояние синтетической проверки и полученные идентификаторы записей |

Секреты и `runtime/` исключены из Git. Подготовка назначает файлам паролей
права `600`, папке секретов — `700`. Значения ключей и паролей в инструкцию,
логи проверки и переписку не выводятся. Для входа используйте имя `admin` и
пароль из локального файла администратора. Для повседневной работы создайте
отдельного обычного пользователя с нужной ролью.

`Settings` читает сначала `.env`, затем `.env.espocrm`; для одинакового имени
параметра второй файл имеет приоритет. Переменные окружения процесса имеют
приоритет над файлами. Команды Python запускайте из корня проекта.
После изменения настроек перезапустите голосовой сервис.

Пароли контейнерной установки передаются через `*_FILE`. Начальные
`ESPOCRM_DATABASE_*` и `ESPOCRM_ADMIN_*` применяются при первой установке;
изменение файла секрета после неё не меняет пароль уже существующей БД или
пользователя. Для смены паролей нужен согласованный процесс изменения самой
системы и её настроек. `ESPOCRM_CONFIG_*` применяются при старте контейнеров.

## Порядок запуска

На машине должны быть запущен Docker Desktop, доступна команда `docker compose`
и подготовлено Python-окружение проекта. Для нового окружения используется
`uv sync --locked`; существующий `.env` не заменяется. Пакет проекта должен
быть установлен в `.venv`, чтобы команды импортировали `voicecrm`.

Выполняйте следующие команды из `/Users/ansar.keles/CRM` последовательно.

### 1. Подготовить локальные пароли

```sh
.venv/bin/python scripts/prepare_espocrm.py
```

Скрипт создаёт отсутствующие файлы секретов и сохраняет существующие значения.
Он не меняет OpenAI/Alem-ключи и не печатает пароли.

### 2. Запустить CRM

```sh
docker compose config --quiet
docker compose up -d
docker compose ps
```

При первом запуске загружаются закреплённые образы, создаётся БД и устанавливается
CRM. Дождитесь состояния `healthy` у БД и приложения. Daemon и WebSocket должны
быть запущены; у них сейчас нет отдельного Compose healthcheck. Для обычного
повторного запуска установка сохраняет существующие данные.

Проверить приложение можно без вывода конфигурации:

```sh
docker compose exec -T espocrm bin/command app-check
docker compose exec -T espocrm bin/command version
docker compose exec -T espocrm bin/command app-info --core-version
```

Версия приложения и core должны совпадать с `10.0.9`. Откройте
`http://localhost:8080` и войдите. Интерфейс настроен на русский язык.

### 3. Подключить ограниченного API-пользователя

```sh
.venv/bin/python scripts/bootstrap_espocrm.py
```

Скрипт использует локальный пароль администратора внутри процесса и создаёт
роль `VoiceCRM Integration` и API-пользователя `voicecrm-api`. Затем проверяет
доступ к Contact и сохраняет API-ключ в `.env.espocrm`. Значения доступов
не выводятся. Повторный запуск использует существующие объекты и ключ.

Если одноимённые роли/пользователи неоднозначны или их права не соответствуют
ожидаемым, скрипт останавливается. Он не должен вслепую заменять чужую роль или
расширять права существующего пользователя. Не устраняйте такой отказ удалением
настроек: сначала проверьте конкретную роль и API-пользователя в интерфейсе CRM.

### 4. Запустить голосовой сервис

Сначала убедитесь, что порт 8001 свободен или принадлежит именно этому проекту.
Если он занят старым экземпляром VoiceCRM, проверьте PID и рабочую папку,
затем завершите его обычным Ctrl+C в соответствующем терминале.

```sh
.venv/bin/python -m uvicorn voicecrm.main:app --host 127.0.0.1 --port 8001
```

Оставьте процесс запущенным. Корневая страница `8001/` теперь перенаправляет
в EspoCRM, а прежний диалог находится на `/voice`.

## Что разрешено голосовой интеграции

| Область | Права текущего API-пользователя |
|---|---|
| Contact | Читать существующие контакты; создавать, менять и удалять нельзя |
| Call | Создавать и читать записи звонков; менять и удалять нельзя |
| Task | Создавать и читать задачи; менять и удалять нельзя |
| User | Читать идентификатор, имя и `userName` для проверки ответственного; чтение остальных полей закрыто настройками роли |
| Администрирование и другие CRM-сущности | Доступ закрыт ролью |
| Экспорт, массовые изменения, data privacy | Запрещены |

Чтение Contact/Call/Task сейчас настроено на `all`, а не только собственные
записи. Назначение ответственного допускается ролью, поскольку EspoCRM проверяет
доступ к связанному User при создании активности. Для нескольких компаний
или команд эти права потребуют отдельной настройки и проверки.

REST-адаптер находится в [src/voicecrm/crm/client.py](../src/voicecrm/crm/client.py).
Он умеет искать контакты по международному телефону, создавать Call/Task,
проверять полученный record id и возвращать фиксированные коды ошибок.
Номер задаётся с `+` и кодом страны; адаптер не угадывает страну по местному номеру.

Публичных HTTP-маршрутов создания CRM-записей в Python-сервисе сейчас нет.
Локальные `/crm/status` и `/crm/contacts` выполняют диагностику и чтение,
проверяют локального клиента/host и источник браузерного запроса. Наличие
адаптера ещё не означает, что языковая модель автоматически создаёт запись
пациента или задачу из разговора.

## Проверки без обращения к OpenAI

### Настройки процесса и реальное соединение

```sh
curl --fail --silent --show-error http://127.0.0.1:8001/health
curl --fail --silent --show-error http://127.0.0.1:8001/crm/status
curl --fail --silent --show-error http://127.0.0.1:8001/realtime/config
```

`/health` сообщает наличие настроек, не вызывает внешние системы. Поэтому
`crm_configured=true` вместе с `crm_connected=null` означает «ключ и URL заданы,
соединение этим запросом не проверялось». `/crm/status` выполняет реальный
запрос Contact к локальной EspoCRM: ожидается `configured=true`,
`connected=true`, `reason=null`.

`/realtime/config` также показывает настройки и не создаёт OpenAI-сессию.
Эти три GET-запроса не являются проверкой микрофона или голосового ответа.

### Полная синтетическая проверка CRM

```sh
.venv/bin/python scripts/verify_espocrm.py
```

Скрипт работает с вымышленным контактом «Тест VoiceCRM» и номером
`+1 (202) 555-0100`. Он проверяет вход администратора, ограниченный API-ключ,
поиск сохранённого форматированного телефона, создание и чтение Call/Task,
связь активностей с контактом, отказ в создании/удалении Contact и закрытие
приватных путей приложения. Звонок и задача имеют названия с `[ТЕСТ]`;
описания явно указывают, что настоящего разговора и записи пациента не было.

Идентификаторы сохраняются в `runtime/verification.json`, поэтому обычный
повтор использует уже подтверждённые записи. Перед POST Call/Task сохраняется
отметка попытки. Если результат создания этих активностей неизвестен, скрипт
отказывается автоматически повторять запрос: предыдущая операция могла
сохраниться в CRM. Тогда найдите
соответствующую тестовую активность в CRM и согласуйте состояние проверки;
не стирайте файл состояния ради повторного запуска. Для первоначального
admin POST Contact такой отметки нет: перед созданием скрипт ищет синтетический
номер, но это не даёт общей гарантии отсутствия дублей при неизвестном результате.

Скрипт не удаляет созданные тестовые активности. Они доступны в интерфейсе
для проверки результата. Эта защита от повторов относится к проверочному
скрипту; постоянная очередь и идемпотентность реальных голосовых событий
пока требуют реализации.

### Локальные тесты кода

```sh
.venv/bin/python -m pytest -q
node --test tests/test_audio.mjs tests/test_realtime_events.mjs
git diff --check
```

Тесты используют синтетические данные и HTTP-подмену. Их результаты дополняют
живую проверку CRM, но не заменяют её.

### Фоновые задания и WebSocket

Проверьте, что daemon запущен, а запланированные задания в административной
панели действительно получают результаты выполнения. `app-check` проверяет
приложение и БД; сам по себе он не доказывает исполнение фоновых заданий.

Для WebSocket проверьте соединение на `ws://localhost:8083`, затем доставку
синтетического уведомления между двумя пользовательскими сессиями. Успешный
handshake подтверждает соединение, но не доставку уведомлений. Факт и границы
выполненной проверки фиксируются в HANDOFF; наличие контейнера не считается
успешной проверкой уведомлений.

## Обычный перезапуск и сохранность данных

Для обычного перезапуска CRM:

```sh
docker compose restart
docker compose ps
```

Дождитесь `healthy` у БД и приложения и запуска daemon/WebSocket, затем
выполните `docker compose exec -T espocrm bin/command app-check`.

После изменения `compose.yaml` применяйте `docker compose up -d`, поскольку
обычный `restart` не пересоздаёт контейнеры с новой конфигурацией. Именованные
тома при этом сохраняются. Проверьте те же Contact/Call/Task и повторите
синтетический verifier: подтверждённые записи не должны размножиться.

Python-сервис перезапускается отдельно после проверки его PID/cwd. Сессии
голосового прототипа пока находятся в памяти и очищаются при перезапуске;
это отличается от постоянных CRM-записей в MariaDB.

Не удаляйте тома, runtime-секреты или `.env.espocrm` для обычного перезапуска.
Удаление томов не является способом обновления или исправления доступа.

## Резервная копия

Полная рабочая копия включает **dump БД, содержимое всех трёх томов EspoCRM
и SQLite-журнал callback**, если сценарий уже использовался.
Отдельно сохраните закреплённый Compose и доступы установки в защищённом
хранилище. Архив `data` содержит внутреннюю конфигурацию и может содержать
вложения и персональные данные; резервная папка должна иметь ограниченный доступ.
[Официальная документация резервных копий](https://docs.espocrm.com/administration/backup-and-restore/).

Ниже — ручная схема для текущего локального Compose. Она временно останавливает
все процессы EspoCRM, способные менять данные, но оставляет БД работающей.
На время копирования закройте CRM, дождитесь завершения текущего подтверждения
и остановите только проверенный процесс голосового сервиса на 8001. Он должен
оставаться остановленным до завершения общей копии: так CRM и журнал операций
относятся к одному состоянию. Чужие процессы и порт 8000 не трогайте.
Команды не печатают секреты; backup не выполняется автоматически этой инструкцией.

Заранее проверьте локальный `CALLBACK_STORE_PATH`: ниже показан стандартный путь.
Шаг SQLite пропускают только если callback никогда не включался и журнал ещё
не создавался. Если обращения уже были, отсутствие журнала означает неполную
копию и требует разбора, а не создания пустой БД.

```sh
umask 077
backup_dir="runtime/backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
docker compose stop espocrm-daemon espocrm-websocket espocrm

# Если callback уже использовался; для нестандартного пути измените --source.
.venv/bin/python scripts/backup_callback_store.py \
  --source runtime/callbacks.sqlite3 --destination "$backup_dir/callbacks.sqlite3"

docker compose exec -T espocrm-db sh -c '
  umask 077
  db_options=$(mktemp)
  trap '\''rm -f "$db_options"'\'' EXIT
  printf "[client]\nuser=espocrm\npassword=%s\n" "$(cat /run/secrets/espo_db_password)" > "$db_options"
  mariadb-dump --defaults-extra-file="$db_options" --single-transaction --databases espocrm
' > "$backup_dir/database.sql"

docker compose run --rm --no-deps --entrypoint tar espocrm \
  -czf - -C /var/www/html data custom client/custom \
  > "$backup_dir/espocrm-files.tar.gz"

cp compose.yaml "$backup_dir/compose.yaml"
docker image inspect espocrm/espocrm:10.0.9 \
  --format '{{json .RepoDigests}}' > "$backup_dir/image-digests.json"

test -s "$backup_dir/database.sql"
tar -tzf "$backup_dir/espocrm-files.tar.gz" >/dev/null
docker compose up -d
```

Выполняйте шаги последовательно и проверяйте код завершения каждого. При
ошибке dump/archive не называйте копию готовой; восстановите обычную работу
через `docker compose up -d`. После запуска дождитесь `healthy`, затем
выполните `docker compose exec -T espocrm bin/command app-check`. Временный файл
с параметрами БД находится внутри контейнера, имеет закрытые права и удаляется
после dump. Одноразовый контейнер tar не запускает установку/миграцию EspoCRM.

Скопируйте готовую резервную копию и необходимые локальные доступы в отдельное
защищённое хранилище. Папка `runtime/backups` остаётся на том же компьютере,
поэтому сама по себе не защищает от потери машины.

`backup_callback_store.py` открывает источник только для чтения, использует
SQLite backup API (включая подтверждённые WAL-данные), проверяет целостность и
создаёт новый файл с правами 600. Существующий файл назначения не перезаписывается.
Сырой `cp` работающей SQLite-БД не заменяет эту процедуру. Если нужно сохранить
синтетическую проверку, отдельно копируйте её журнал и файл состояния в то же
защищённое хранилище; их содержимое в отчёт не выводите.

Восстановление сначала проверяйте в отдельном Compose-проекте с отдельными
томами и портами: используйте сохранённые версии, импортируйте dump в новую
БД, восстановите `data/custom/client/custom` и копию SQLite-журнала по
`CALLBACK_STORE_PATH` с правами 600, сопоставьте доступы, выполните `app-check`,
проверьте записи и права API-пользователя. Убедитесь, что статусы и receipt
callback сохранены, а повтор уже отправленной операции не делает новый POST.
Успешный список файлов
архива не доказывает возможность восстановления. Текущий рабочий экземпляр
не используйте как пробный стенд восстановления.

## Исходники и изменения проекта

Папка [espocrm/](../espocrm/) содержит файлы официального **собранного релиза**,
экспортированные из image `espocrm/espocrm:10.0.9`. Это не Git checkout:
попытки получения Git-исходников завершались двумя сетевыми тайм-аутами.
Происхождение записано в [SOURCE.json](../espocrm/SOURCE.json).
Экспорт исключает рабочие `data`, `vendor` и секреты. Полного дерева разработки,
lockfiles, исходных frontend-модулей и upstream-тестов в снимке нет.

Этот снимок предназначен для анализа; работающая CRM загружает core из Docker
image. Редактирование локального `espocrm/` не изменяет установленную CRM.
Скрипт [export_espocrm_source.py](../scripts/export_espocrm_source.py) позволяет
получить снимок после запуска и отказывается перезаписывать существующий
экспорт. Полноценная разработка core потребует точных исходников upstream
и отдельной сборки; `master` не подменяет закреплённый релиз.

Наши изменения выполняются в Python-адаптере и штатных расширениях EspoCRM:
`custom/Espo/Modules/` и `client/custom/`. Метаданные, поля и layouts можно
настраивать через Entity Manager; более сложные изменения оформляются
installable extension. Core и собранные `client/lib/espo*.js` вручную не
правим. Сохраняем лицензию и предусмотренные upstream обозначения EspoCRM.
[Разработка расширений](https://docs.espocrm.com/development/how-to-start/).

Обновление версии CRM выполняется отдельно: резервная копия, проверка
совместимости расширений на стенде, согласованная смена версии web/daemon/WS,
миграция и повторная проверка. Compose закреплён на `10.0.9`; простой pull
не переводит его на следующую версию. Версию MariaDB также не меняйте
одновременно без отдельного плана восстановления.

## Если что-то не работает

| Симптом | Следующий шаг |
|---|---|
| Compose сообщает об отсутствующем secret-файле | Выполнить `prepare_espocrm.py`; не подставлять стандартный пароль |
| БД или EspoCRM не становится `healthy` | Проверить состояние сервисов и ограниченный фрагмент локальных логов; не публиковать тела конфигурации и секреты |
| `/health` показывает `crm_configured=false` | Завершить bootstrap и перезапустить Python из корня проекта |
| `/crm/status`: `authentication` | Проверить API-пользователя, активность и соответствие сохранённого ключа; наличие файла не подтверждает действительность ключа |
| `/crm/status`: `forbidden` | Проверить единственную роль `VoiceCRM Integration` и разрешение чтения Contact |
| `/crm/status`: `unavailable` | Проверить EspoCRM на 8080, `app-check`, URL и timeout |
| Verifier сообщает `write_unconfirmed` или прежнюю неподтверждённую попытку | Сверить существующую `[ТЕСТ]` активность и состояние проверки перед повтором |
| На `8001/` видна CRM, а не микрофон | Открыть `8001/voice`; корень теперь намеренно перенаправляет в EspoCRM |
| CRM открывается, но уведомления не приходят | Проверить WS URL 8083, процесс WebSocket и доставку между сессиями |

Для проверки настройки Compose используйте `docker compose config --quiet`.
Не передавайте полную конфигурацию, окружение контейнеров, `.env*`, записи
звонков или полные логи в публичный отчёт.

## Обращение на обратный звонок

15 октября добавлен первый подтверждаемый сценарий для обычного `/voice`
(текстовый OpenAI и файловый Alem STT). Realtime пока его не вызывает.
По умолчанию сценарий отключён: задайте `CALLBACK_ASSIGNEE_ID` разрешённого
сотрудника в локальной конфигурации и перезапустите голосовой сервис.
Автоматического выбора администратора нет. `CALLBACK_STORE_PATH` по умолчанию
равен `runtime/callbacks.sqlite3`; его нельзя заменять временной БД.

Помощник уточняет телефон с кодом страны и содержание обращения, затем
`prepare_callback` проверяет пользователя и совпадения контактов, сохраняет
неизменяемый черновик и возвращает его на страницу. Модель не получает
инструмент подтверждения и не выбирает ответственного. Можно также открыть
форму «Попросить обратный звонок». При одном совпадении контакт привязывается;
при нескольких клиент выбирает контакт в форме и снова нажимает «Проверить
обращение», при нуле Task создаётся без Contact. Инструмент модели не может
подтвердить выбор одного из нескольких кандидатов, даже передав известный ID.
Выбранное имя показывается в карточке и сохраняется вместе с черновиком;
у старых операций имя может отсутствовать, тогда интерфейс показывает ID.
Двадцать совпадений считаются потенциально усечённым поиском и блокируют
подготовку. Телефон сам по себе не подтверждает личность клиента.

Клиент проверяет контакт, телефон и пожелания, нажимает «Подтвердить заявку» либо
отправляет точную фразу «Подтверждаю заявку». Произвольное «да» не подтверждает
черновик. Новая реплика с пожеланиями отменяет старый draft; исправленные
данные требуют нового подтверждения. Перед POST повторно проверяются
ответственный и контакты. Статус «Задача создана в CRM» формируется сервером
после receipt EspoCRM. Task означает обращение сотруднику, не медицинскую запись.

Форма и диалог используют общий серверный снимок проверенных полей черновика.
Например, после формы «Чистка в пятницу после 15:00» реплика «Лучше в субботу»
получает прежние телефон, услугу и время как контекст для нового черновика.
Более старая переписка до этого снимка не передаётся модели. После уточняющего
ответа или ошибки модели исходные проверенные поля сохраняются; неудавшаяся
реплика, как и прежде, не добавляется в историю — её нужно повторить.
Явная отмена или завершение обращения очищают его рабочий контекст. Повторная
передача браузером прежнего UUID не стирает уже начатое новое обращение.
Имя/ID контакта в снимке являются данными, а не правом модели выбрать клиента
при нескольких совпадениях: выбор по-прежнему требуется в форме.

В callback-режиме ответы без инструмента имеют строгий `reply_code`: текст
выбирается из серверных шаблонов, свободное сообщение модели не озвучивается.
Это ограниченный сценарий обратного звонка до подключения знаний компании.
Серверные шаблоны пока русскоязычные; другие языки добавляются отдельно.
Потерянный callback ID возвращает отдельный код `not_found` и не портит сессию.
Сетевой сбой при восстановлении UUID сохраняет запрет нового обращения до сверки.
Неактивные текстовые сессии истекают через 1800 секунд
(`SESSION_IDLE_TIMEOUT_SECONDS`); операции SQLite переживают это истечение.

Локальный API (same-origin и loopback, мутации с JSON):

| Метод | Путь | Результат |
|---|---|---|
| POST | `/crm/callbacks` | Черновик из `phone`, `summary`, необязательного `contact_id`; `session_id` связывает с диалогом, `previous_id` учитывает предыдущее обращение |
| GET | `/crm/callbacks/{id}` | Сохранённый статус, без отправки задачи |
| POST | `/crm/callbacks/{id}/confirm` | Явное подтверждение, тело `{}` |
| POST | `/crm/callbacks/{id}/cancel` | Отмена только локального черновика, тело `{}` |
| POST | `/crm/callbacks/{id}/reconcile` | Только GET-сверка результата CRM, тело `{}` |

Статусы: draft → dispatching → succeeded / failed / unconfirmed; draft также
можно отменить. SQLite атомарно фиксирует dispatching до сети. Для одного UUID
операции допускается не более одной попытки POST, в том числе при параллельном
подтверждении и перезапуске. При неопределённом результате выполняется поиск
Task по точному серверному имени с UUID и сравнение описания, ответственного
и parent. Нулевой результат не разрешает повторный POST. Пока результат
неопределён, интерфейс/тот же диалог блокируют подготовку нового обращения.

Сервис выполняет SQLite-операции в рабочих потоках: ожидание блокировки БД
не останавливает обработку других разговоров. Отмена HTTP-обработчика не
прерывает уже запущенную транзакцию SQLite. Если claim успел сохраниться после
отмены, операция остаётся dispatching и требует сверки; повторный POST запрещён.
При коррекции сервис завершает локальную отмену прежнего черновика и сохраняет
его проверенные поля под блокировкой сессии, даже если запрос был отменён.
Следующая реплика сохраняет исходные данные; отменённую реплику нужно повторить.

Это постоянный журнал операций, ещё не автоматический outbox: сбой после
dispatching, но до POST может оставить обращение без задачи. Тогда нужна
сверка и, при необходимости, ручной разбор. Новый UUID обозначает отдельную
операцию; защита не объединяет произвольно созданные одинаковые обращения.
Изменение Task сотрудником или потеря SQLite могут помешать сверке.
Не удаляйте БД для повторной проверки. Она содержит телефоны и обращения,
имеет права 600, исключена из Git и требует защищённого резервирования.

Синтетическая живая проверка использует отдельные файлы
`runtime/callback-verification.sqlite3` и `runtime/callback-verification.json`:

```sh
.venv/bin/python scripts/verify_callbacks.py --synthetic-bootstrap-assignee --with-openai
.venv/bin/python scripts/verify_callbacks.py --synthetic-bootstrap-assignee
```

Первая команда явно выбирает ответственного из прежнего синтетического
bootstrap и при отсутствии сохранённой операции вызывает платный OpenAI.
Это не настраивает ответственного работающего сервера. Вторая команда из
нового процесса повторно использует тот же UUID без модели и нового POST.
Синтетическая summary начинается с `[ТЕСТ]`; такие Task получают этот префикс
и в имени. Скрипт проверяет ровно одну Task, все поля и повторный receipt;
неизвестный результат сохраняется и не повторяется новым UUID автоматически.

Проверено 15 октября: живой OpenAI подготовил черновик, явное подтверждение
создало одну `[ТЕСТ]` Task в EspoCRM, повторный запуск подтвердил тот же результат
без дубля. Это проверка текстового сценария и API, без микрофона, браузерного
озвучивания и Realtime. Управление Chrome средой не разрешено; визуальная
приёмка новой карточки не выполнена.

## Что делаем дальше

Дальнейшая работа — выбрать реального ответственного и компанию, принять
сценарий callback в браузере/микрофоне, подключить утверждённые знания и
серверные инструменты Realtime. Для автоматической гарантированной доставки
нужен следующий слой outbox и уникальный внешний ключ операции в EspoCRM.
Затем — сценарий бронирования, SIP/Asterisk, записи и анализ звонков.

Создание записи Call подтверждает CRM-активность, а не настоящий телефонный
звонок. Task не подтверждает запись пациента. Эти результаты определяются
соответствующими системами и проверяемыми операциями.

Цель около одной секунды до первого слышимого ответа остаётся отдельной
задачей голосового ядра. Установка EspoCRM и успешный HTTP-запрос к её API
не доказывают такую скорость. Границы Realtime-таймера и порядок живой проверки
описаны в [REALTIME.md](REALTIME.md).
