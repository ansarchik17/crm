## Настройки и ключи

Приложение читает `.env` относительно рабочего каталога. Раньше ключи были в
`.env.example`, а `.env` отсутствовал. Создали `.env`, включили API.
Позже значения ключей удалили из `.env.example`; настоящие остаются в локальном `.env`.
Не выводить содержимое `.env` или ключи в чат, логи, отчёты и шаблоны.

Рабочая конфигурация без секретов:

```dotenv
LLM_MODE=qwen
QWEN_BASE_URL=https://llm.alem.ai/v1
QWEN_MODEL=qwen3-8
QWEN_ENABLE_THINKING=false
LLM_TIMEOUT_SECONDS=15
STT_ENABLED=true
STT_BASE_URL=https://llm.alem.ai/v1
STT_MODEL=speech-to-text
STT_TIMEOUT_SECONDS=60
```

Ключи имеют имена `QWEN_API_KEY` и `STT_API_KEY`. Не просить пользователя вводить
их заново без проверки наличия — он уже добавил действующие ключи.
Исходные модели `qwen3-6` и `speech-to-text-kk` возвращали 403: ключи разрешают
соответственно `qwen3-8` и `speech-to-text`. Исправление подтверждено живыми запросами.

## Задержка и выполненное ускорение

Первый тест: STT около 3,5 с, Qwen около 10,5 с.
Затем сделали сравнительные запросы. Одинаковые запросы, похоже, кэшируются:
совпадали ответы и число токенов даже при разных параметрах. Нельзя приписывать
всё ускорение настройкам на основании повторного запроса.

Серия с уникальным идентификатором в системном промпте, 3 вопроса на каждый режим,
чередование режимов, max_tokens=256:

- Исходный режим: 5,837 / 2,496 / 7,561 с; только 1 из 3 полных ответов.
- `/no_think` в промпте: 3,266 / 4,965 / 2,409 с; только 1 из 3 полных ответов.
- `chat_template_kwargs: {"enable_thinking": false}`: 0,856 / 1,217 / 0,612 с;
  все 3 ответа полные, поле рассуждений пустое, 19–40 токенов.

Проблема исходного режима: внутренние рассуждения съедали лимит, API возвращал
HTTP 200, content=null, finish_reason=length. Не сохраняли текст рассуждений.
Добавили `qwen_enable_thinking: bool | None = None` в Settings и условную передачу
`chat_template_kwargs` в QwenModel. При отсутствии настройки поле не отправляется.
В локальном `.env` выставили false. Лимит 256 оставили.

Повтор голосового после изменения: STT 2,358 с, Qwen 0,325 с, вся цепочка 2,699 с.
Возможен кэш; это не гарантия такой скорости на новых вопросах или под нагрузкой.
Тесты: `.venv/bin/python -m pytest -q` — 28 passed; одно предупреждение Starlette/httpx.

Пользователь считает, что API безлимитные. Квоты аккаунта, тарифы и rate limits
НЕ проверяли. `max_tokens=256` — наш параметр запроса, а не доказательство лимита тарифа.
Ошибок превышения квоты в тестах не было.

### Диагностика задержки Qwen

Пользователь предположил, что медленный ответ связан с Qwen. Добавлен ручной
`scripts/benchmark_response_latency.py` (6 запросов, возможна тарификация).
28 сентября выполнены 3 пары новых вымышленных запросов, чередование stream,
уникальный идентификатор в системном промпте каждого запроса, общий HTTP-клиент.
Модель `qwen3-8`, thinking=false, max_tokens=256, текущий стоматологический промпт.
Обычные полные ответы: 4,797 / 1,591 / 0,646 с.
Потоковые: первый непустой текст 0,533 / 0,970 / 0,407 с;
полные ответы 0,807 / 1,470 / 0,615 с. Все завершились stop.
Alem фактически вернул SSE, 13–22 порции текста и [DONE]: streaming подтверждён
для этого endpoint и ключа. В приложение streaming ещё НЕ подключён.
Первые завершённые предложения в этих запросах — короткие приветствия;
не считать время первого предложения задержкой содержательного ответа.
Малая выборка, разные ответы и их длина, первый запрос на холодном соединении:
сравнение не доказывает, что streaming ускоряет генерацию в несколько раз.
Измеряется API вместе с сетью, не чистое вычисление модели. STT/TTS в тесте нет.
Результат: `recordings/response_latency_20260928T102128Z.json`.
Отдельный файл с суффиксом `102040Z` содержит только ConnectError песочницы,
не использовать как данные о доступности/быстродействии провайдера.

### Веб-страница и браузерное озвучивание

Добавлена страница `http://127.0.0.1:8000/`, файлы в `src/voicecrm/static`.
Микрофон: AudioWorklet, mono PCM16 WAV 24 кГц, до 29 секунд. После остановки
браузер последовательно вызывает `/transcriptions` и сообщения текущей сессии,
затем SpeechSynthesis. Есть текстовый ввод, WAV-файл, выбор голоса, остановка
озвучивания, повторное прослушивание, новый диалог, сообщения об ошибках.
Ключи остаются на сервере. Серверный TTS не добавлен; `tts_connected=false` верно.
Голоса устройства: в Chrome найден русский локальный Milena, он выбран по умолчанию.
Онлайн-голоса отдельно помечены; они могут передавать текст своему поставщику.

Проверки: 29 Python-тестов и 4 Node-теста прошли. Node проверяет WAV-заголовок,
PCM, смешивание каналов, ручную остановку и лимит 29 секунд. В Chrome проверен
живой текстовый диалог с Qwen; ответ за 1,1 с, SpeechSynthesis сообщил завершение
озвучивания («Озвучено»), в консоли нет ошибок. Качество голоса на слух агент
не оценивал. Скриншот: `recordings/dental-ui.png`. Реальная запись микрофона пока требует проверки
пользователем и разрешения браузера. Автоматическая загрузка WAV через расширение
не прошла из-за отсутствия разрешения расширению читать file URLs; настройки
расширения не менялись. Это ограничение инструмента проверки, не ответ API.
Uvicorn запущен заново на 127.0.0.1:8000 с актуальным кодом. При новом сеансе
проверить доступность процесса. У страницы нет сборки; после JS/CSS-правок
нужна перезагрузка, после Python-правок — перезапуск сервера.

Источники Web API: https://developer.mozilla.org/en-US/docs/Web/API/Window/speechSynthesis
и https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia.
